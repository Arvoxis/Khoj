KHOJ - Technical Architecture Summary

Executive Overview

KHOJ is an autonomous drone swarm for search & rescue that operates without a central controller. Drones coordinate via a leaderless market auction, confirm survivors with a second independent sensor, and operate on a mesh of \$5 ESP32 boards. The system combines Python simulation, real detector inference on a Jetson edge device, and embedded firmware for decentralized decision-making.

Complete Tech Stack

1. Swarm Engine (Python)

Location: engine/
Core Modules: world.py, swarm.py, belief.py, protocol.py, run_sim.py, perception.py

Purpose: Simulate and run the real swarm coordination logic.

  • World Simulation: 60×40 grid world with hidden survivors, RSSI fields, knowledge maps
  • Swarm Coordination: Leaderless auction where drones bid expected_survivors/sec; highest bid wins (ties → lowest agent ID)
  • Belief Fusion: Bayesian log-odds per survivor. Requires ≥2 independent agents for confirmation (no self-confirmation)
  • Trust Model: Per-agent Beta prior. Faulty sensors auto-quarantine after poor predictions
  • Perception Projection: Maps nadir camera boxes to world coordinates using pinhole camera model (altitude 30m, hfov 66°)

2. Real Detector (Jetson)

Location: detector/
Files: train.py, export_jetson.py, jetson_cam_demo.py, jetson_stream.py

Purpose: Run trained YOLO inference on the drone's onboard compute.

  • Model: YOLOv11n trained on 1,200 real aerial SAR images (SARD dataset), then fine-tuned for indoor/collapsed-building scenes on the Kaggle C2A dataset — see detector/khoj_indoor.yaml, which is the active detector config
  • Accuracy: mAP50 0.934, recall 0.875
  • Optimization: Quantized to FP16 TensorRT engine (device-specific, built on Jetson)
  • Speed: Single-digit ms/frame on Orin (inference-only)
  • Live Demo: jetson_stream.py serves MJPEG (live boxes + confidence) to browser at http://192.168.55.1:8090

3. Hardware (ESP32 Mesh)

Location: khoj/firmware/
Files: src/mesh/main.cpp, src/agent/main.cpp, lib/quorum_proto/quorum_proto.h

Purpose: Decentralized on-device coordination on 5 ESP32 boards.

  • Protocol: ESP-NOW mesh, 5 Hz heartbeat, 28-byte sensor frames + 17-byte goal frames
  • On-Device Auction: Each board prices incoming sightings and bids for tasks—no laptop referee
  • Failure Detection: Peer dead in <2 seconds; re-auction triggered automatically
  • RF Localization: Hill-climb to transmitter across distributed RSSI readings
  • Wire Contract: quorum_proto.h ↔ khoj/sim/protocol.py (byte-identical)
  • Performance: 0% packet loss @ 5 Hz over bench test

4. Dashboard & Visualization

Location: frontend/, backend/, dashboard/

Purpose: Real-time mission console showing swarm state, coverage, belief, and auction progress.

  • Backend: FastAPI + WebSocket (state updates 10 Hz)
  • Frontend: Canvas-based 2D visualization (index.html, app.js, styles.css)
  • State Adapters: 3 modes—fake (mock), real (Python engine), hardware (5 live boards)
  • Data Rendered: Agent positions/headings, open tasks, candidate survivors, confirmed survivors, trust scores, coverage heatmap

5. Integration Layer

Location: khoj/sim/

Purpose: Bridge between detector, swarm engine, and hardware boards.

  • feeder.py: Reference HIL feeder (parses goal frames, streams sensor frames over serial)
  • feeder_real.py: Jetson-side bridge. Feeds real YOLO detections + RSSI to boards via USB serial
  • wire_test.py: Validates protocol byte-stream in isolation

Why This Architecture

Design Choice Problem It Solves
Leaderless Auction No single point of failure. Drones re-coordinate in <2s if leader drops
Confirmation (≥2 agents) 0 false alarms. Structural rule: one sensor can never confirm, by design
Trust & Quarantine Faulty/spoofed sensors auto-bench. Swarm keeps working at reduced efficiency
On-Device Belief Decentralized: boards make decisions, not waiting for laptop comms
Jetson Edge Detector Real drone compute. Not simulated—trained on actual SAR imagery, runs on device
ESP32 Mesh Cheap (\$5 ea), scalable, no single router. Adds 5 more drones = add 5 boards

Proven Performance

Survivors Confirmed: 4.23 (equal time budget vs. greedy 1.67 / lawnmower 1.40 / random 2.63)
False Alarms: 0 across 600 Monte-Carlo runs
Detector Accuracy: mAP50 0.934, recall 0.875 (trained on real SARD imagery)
On-Device Speed: ~6 ms/frame on Jetson Orin (inference)
ESP-NOW Mesh: 0% packet loss @ 5 Hz, 5 boards
Failure Detection: Dead peer recognized in < 2 seconds, auction re-runs automatically
RF Localization: Converges to ±0.3 grid cells (finds transmitter no drone can see)

How It Works (Mission Flow)

  1. Setup: 5 ESP32 boards boot on ESP-NOW mesh. Jetson boots with TensorRT engine ready. Laptop runs dashboard backend + WebSocket server.
  2. Coverage Phase: Each board runs the frontier auction itself and decides alone which cell to claim — the laptop never assigns goals. In the hardware-in-the-loop demo the laptop supplies sensor packets and simulates motion, terrain and RSSI; the decision is always the board's.
  3. Detection Phase: Jetson camera sees a person → runs YOLO → 0.81 confidence → sends usb_sensor_t to board.
  4. Auction Phase: Board receives detection, creates REOBSERVE task. All boards bid (pricing = estimated log-odds gain). Board A wins.
  5. Re-observation Phase: Board A navigates to coordinates. Second drone (B) arrives from different bearing, runs YOLO again → sees person at 0.92.
  6. Confirmation Phase: Laptop fuses two independent observations (0.81, 0.92 from different angles) → log-odds = 4.2 → CONFIRMED (survivor found).
  7. Next Auction: Remaining boards bid for frontier tasks. No pilot, no controller. Repeat until mission complete.
